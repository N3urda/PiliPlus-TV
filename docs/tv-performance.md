# Android TV 性能检查（v0.3.4）

## 面向 2 GB 电视的改动

- TV 图片缓存上限从 48 MiB / 120 张收紧至 32 MiB / 96 张。系统通知内存压力后降至 16 MiB / 48 张，本次进程内保持较小预算；切到后台清理可复用缓存，不清除仍在屏幕上使用的图片引用。
- 视频卡片焦点框即时更新，移除 120 ms 装饰渐变，减少切换焦点时反复重画封面和文字阴影，不增加额外卡片纹理缓存。
- 首页封面最大解码尺寸 360×203，普通 16:9 封面相较此前 420 像素宽约减少 26% 的像素内存。搜索和相关推荐限制在 560×315，使用 fit 保留比例，异常长图也受高度约束。
- 封面模糊、底色和文字可读性渐变在 256×144 小图上合成一次。稳定背景每帧由 4 次全屏绘制降至 1 次，封面交替由 5 次降至 2 次。这是绘制指令数量，不能等同于帧率提升比例。
- 背景最多持有两张已合成图片，像素数据约 288 KiB；后台或内存压力时释放，过期异步结果立即丢弃。
- 关闭 TV 弹幕时不创建画布、控制器与播放监听；从开启切为关闭会释放这些对象，迟到的网络/本地数据不会重新填充已销毁的弹幕缓存。
- 搜索只保留播放和展示所需字段、按 BV 号去重，空页停止继续请求；分页追加不再复制整份结果列表。首页和搜索继续按视口懒加载，预加载距离 128 逻辑像素，不裁剪已加载视频。
- 没有保存过画质偏好的 TV 首次使用默认 1080P，已保存偏好不覆盖，用户仍可手动选择其他画质。实体电视保留 MediaCodec 硬件解码；原有压缩缓冲为前向 4 MiB、后向 4 MiB。

## 验证方式

- 36 项 TV 测试通过；涵盖 1000 条列表滚到底再返回、异常长封面实际解码、侧栏焦点、背景异步释放、弹幕开关与内存压力策略。1000 条数据不同时构建为 1000 张卡片，测试视口中存活卡片少于 40 张。
- `flutter analyze --no-pub lib/tv lib/pages/danmaku lib/main.dart test/tv` 无问题。
- Android TV 14 / arm64 模拟器，1920×1080，`MemTotal=2025912 kB`，约 2 GB。
- `tools/tv/performance_smoke.py` 保存每阶段截图、前台 Activity、PSS/RSS 和日志；验证应用确实在前台，并人工确认截图中已播放视频。模拟器同时存在其他宿主任务，数据用于本轮诊断，不能代表实体电视的 SoC 性能。
- 可选构建参数 `--dart-define=TV_PERF_PROBE=true` 每 5 秒汇总已渲染 Flutter 帧的 build/raster 耗时、超预算帧数与图片缓存。正式发布包不传此参数，采样器默认关闭。
- `over_16ms` / `over_33ms` 指构建或光栅阶段任一超过预算的帧，不能当作视频丢帧率；Android `gfxinfo` 不反映本应用全部 Flutter 帧，因此不用于宣称 60 FPS。图片缓存字节也不代表整个进程占用。

## 本轮模拟器实测

### 内存与生命周期

2026-09-26 软件渲染模拟器，v0.3.4 采样包三次播放返回的 PSS 为 **181.97 → 178.63 → 179.23 MiB**，静置后 **171.15 MiB**。通知内存压力后 **168.04 MiB**，后台再恢复为 **168.82 MiB**。日志确认缓存预算 **32 → 16 MiB**，可复用缓存从 **5.05 MiB → 0**，同时保留 18 张活跃图片；不代表所有图片内存归零。

2026-09-28 启用宿主 GPU（SurfaceFlinger：Apple M4 / OpenGL ES Translator / Metal）后，五轮播放流程的 PSS：

| 场景 | PSS |
| --- | ---: |
| 冷启动首页 | 155.52 MiB |
| 连续浏览后 | 158.13 MiB |
| 五轮播放范围 | 265.21–273.20 MiB |
| 各轮返回首页 | 191.41 → 203.03 → 207.99 → 200.08 → 185.20 MiB |

五张播放截图均显示同一视频的实际画面，五次返回与后台恢复截图均回到首页、焦点可见。未发现应用相关崩溃、OOM 或 ANR 日志。第五次播放在 08:00:19.937 出现 BUFFERING，08:00:21.063 恢复 PLAYING，约 1.13 秒；不声称全程无缓冲。所有采样阶段进程 PID 一致，返回内存没有单调持续增长。这是短流程稳定性证据，不证明长时间无泄漏。推荐流随时间变化，两次测试播放了不同视频，软件/宿主 GPU 模式也不同，因此不把这些数字当成严格 A/B 的优化降幅。

### 界面帧耗时

软件渲染运行的两个完整浏览窗口，共 311 帧：build 平均 0.401 ms，raster 平均 27.884 ms，窗口 raster P95 为 44.076 / 39.263 ms。软件渲染成为主要限制。

宿主 GPU 运行的两个完整浏览窗口，共 468 帧：build 平均 0.731 ms，raster 平均 10.772 ms，窗口 build P95 为 1.254 / 2.077 ms，raster P95 为 24.351 / 30.671 ms；104 帧的构建或光栅阶段超过 16.667 ms，14 帧超过 33.333 ms。这些记录来自卡片焦点即时响应改动之前，显示仍有耗时尖峰；没有据此宣称稳定 60 FPS。

改为焦点即时响应后，以相同方向键脚本补测：两个完整浏览窗口共 46 个实际渲染帧，build 平均 **0.381 ms**，raster 平均 **2.363 ms**；窗口 build P95 为 **0.518 / 0.534 ms**，raster P95 为 **3.279 / 2.891 ms**，这 46 帧中没有构建或光栅阶段超过 16.667 ms。焦点装饰不再为每次移动产生 120 ms 动画帧。不同推荐封面与运行热身状态会影响结果，因此不将此样本解释成确定的性能提升百分比或全程零卡顿。

最终代码的采样包补测 PSS：冷启动 **153.32 MiB**，浏览后 **161.01 MiB**，该次视频播放 **297.83 MiB**，返回 **232.68 MiB**，静置 **209.41 MiB**，内存压力后 **206.60 MiB**，后台恢复 **205.05 MiB**。这次推荐视频又有变化，进一步表明播放内存取决于视频内容；不能只挑较低数值作为整个版本的占用。

### 实体电视验收

模拟器中的视频采用软件解码，无法代替目标电视的 MediaCodec、显存与系统后台负载。安装本次 APK 后，应在目标 2 GB 电视上检查连续浏览、搜索分页、长视频播放、快进以及多次返回，尤其是手动选择 4K/高帧率内容的情况。当前版本可供安装验证，尚未作出目标机型稳定 60 FPS 的结论。

## 历史记录

### Android TV 内存与列表检查（v0.3.1）

## 发现与改动

- 当前 Flutter SDK 的解码图片缓存默认上限为 100 MiB。TV 模式改为 48 MiB、最多 120 张图片；离开屏幕较远的图片可以更早被回收。
- 搜索页原先用 `Wrap` 同时创建全部已加载结果。80 条结果的回归测试在修改前创建了 80 张卡片，改为懒加载网格后，1080p 视口首帧创建少于 12 张。
- 首页和动态网格、搜索结果网格的预加载距离设为 128 逻辑像素。搜索卡片的图片解码宽度由 600 降到 560 像素。
- 播放画质与实体电视上的硬件解码策略保持原设置；本轮不通过降低画质换取内存。
